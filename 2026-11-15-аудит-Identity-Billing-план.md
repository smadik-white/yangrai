# Аудит ТЗ Identity/Billing и план интеграции

**Дата:** 15.11.2026
**Предмет:** `YANGRAI_TZ_Identity_Authorization.md` (v1.0), `YANGRAI_TZ_Billing_Payments.md` (v1.0)
**Что проверялось:** `smm-studio` (продукт), `yangrai-ai-promotion` (сайт), инфраструктура encake.site

---

## 1. Резюме для решения

1. **Оба ТЗ написаны грамотно** — принципы (OIDC, не дублировать пароли, идемпотентность платежей, снимок тарифа, не доверять скриншотам) правильные. Проблема не в качестве, а в **объёме и в трёх нерешённых зависимостях**.
2. **Блокер №1 — RAM.** Keycloak (JVM) требует ~1–2 ГБ. Текущий контейнер — 384 МБ, Node уже ограничен `--max-old-space-size=256`. Нужен отдельный VPS ≥2 ГБ (~300–600 ₽/мес) либо другой IdP.
3. **Блокер №2 — YANGRAI Core не существует.** Оба ТЗ опираются на сервис (профили, организации, членство, entitlements), которого нет ни в виде кода, ни в виде схемы. «Интеграция» = построить два новых сервиса + переделать продукт.
4. **Блокер №3 — домены не выбраны.** SSO, redirect URI и cookie-модель нельзя спроектировать, пока не решено, на каком домене живёт IdP и останется ли кабинет на `encake.site`.
5. **Billing в объёме ТЗ — 6–12 месяцев для команды.** Для первых продаж нужен жёсткий срез (без CRM, КП, AI-кредитов, массовых возвратов). Полный объём имеет смысл только после первых платящих клиентов.

**Оценка:** «первый рубль» (вход + организация + изоляция данных + ручная оплата) — **~120–170k токенов**, 3–4 недели. Полный объём по обоим ТЗ — **~400–600k**, 6–10 недель.

## 3. Аудит ТЗ Identity & Access Management

### 3.1. Что сделано хорошо

- Чёткое разделение: Identity = аутентификация, Core = бизнес-профиль/организации/подписки, Products = продуктовые права.
- Явно запрещено делать IdP источником тарифных правил (§2) — это правильная граница.
- «Email не является первичным ключом», «нельзя объединять аккаунты по непроверенному email» (§6) — закрывает классическую уязвимость.
- Требование проверять права на backend, а не в UI, и явно упомянут IDOR (§9) — редкость для ТЗ.
- «Не создавать параллельные таблицы паролей/сессий» (§12) и «не реализовывать свои алгоритмы» (§8) — правильные ограничители.

### 3.2. Проблемы

| # | Проблема | Почему важно |
|---|---|---|
| I-1 | **Keycloak не проходит по ресурсам.** Prod-гайд Keycloak — 2 CPU / 2 ГБ; реально нужно ≥1 ГБ heap. Контейнер 384 МБ, из них Node ест 256 | ТЗ требует «аудит инфраструктуры», но бюджет не посчитан. Нужен отдельный VPS или другой IdP |
| I-2 | **SSO и домены противоречат друг другу.** Кабинет на `encake.site`, бренд — `yangrai.ru`, сайт без домена | Общая cookie-SSO возможна только в одном registrable domain. Между разными доменами — только OIDC-редиректы. Модель не зафиксирована |
| I-3 | **Граница «своих» сессий размыта.** §12 запрещает параллельные таблицы `sessions`, но продукту нужна cookie-сессия | Нужно явно разрешить `product_sessions` (BFF-сессия продукта), иначе неясно, как продукт держит вход |
| I-4 | **Не сказано, где живут глобальные роли.** §9 перечисляет `SuperAdmin/Admin/Manager/Support/User`, но не говорит — Identity или Core | Разъезд ответственности → дублирование ролей в двух сервисах |
| I-5 | **Админка (§13) и личный кабинет (§14) не входят в этапы (§17).** В этапах нет ни одного пункта про UI пользователя/администратора | Объём скрыт: это ещё 2 интерфейса |
| I-6 | **BFF упомянут как «если подходит»**, хотя для SMM Studio он обязателен (§7 запрещает токены в localStorage) | Нужно зафиксировать: Express = BFF, токены только на сервере |
| I-7 | **Нет требований к SMTP.** Подтверждение email и сброс пароля без почтового провайдера не работают | Внешняя зависимость + расход, в ТЗ не учтены |
| I-8 | **§16 (152-ФЗ) не связан с §4 (выбор IdP).** Требование локализации ПДн в РФ фактически исключает зарубежные SaaS-IdP | Выбор IdP надо ограничить self-hosted в РФ — иначе противоречие внутри ТЗ |
| I-9 | **Миграция описана как «сохранить существующих пользователей», но их нет** | Реальная миграция = создать первого владельца и привязать текущие проекты/каналы к первой организации. В ТЗ этого нет |
| I-10 | **Нет staging.** §11 требует отдельных redirect URI для prod/staging/dev, но окружения нет | Настройка auth на проде без staging — риск запереть себя снаружи |

### 3.3. Мой вывод по IdP

| Вариант | RAM | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| **Keycloak** | ~1–2 ГБ | Из коробки: email-verify, сброс пароля, brute-force, сессии, админка, MFA, темы | Java, отдельный VPS, операционный груз | ✅ **основной** — если выделить VPS 2 ГБ |
| Zitadel | ~300–500 МБ | Go, организации и членство встроены, современный UI | Свои организации дублируют Core | ⚠️ резерв, если RAM критична |
| Ory Kratos/Hydra | ~150–300 МБ | Модульность, лёгкость | Два сервиса, сложная настройка, всё UI писать самому | ⚠️ для опытной команды |
| `oidc-provider` (panva, Node) | ~100 МБ | Тот же стек, влезает в текущий сервер | Регистрацию, verify, reset, защиту от перебора, админку писать самому — 1500–2500 строк, и это security-sensitive | ❌ не рекомендую как основу |
| Auth0 / Clerk / Supabase Auth | — | Быстрый старт | Зарубежные, ПДн за границей, оплата | ❌ противоречит §16 |

**Рекомендация:** Keycloak на отдельном VPS ≥2 ГБ, организации держать **не в нём**, а в Core (как и требует ТЗ §2). Тогда IdP закрывает §5, §7, §8, §13, §14 почти целиком, и остаётся написать только Core.

## 4. Аудит ТЗ Billing & Payments

### 4.1. Что сделано хорошо

- Деньги — целые в копейках, даты — UTC, запрет хранить карты, подтверждение только по ответу провайдера.
- **Снимок тарифа в заказе** (§4) — то, что обычно забывают и потом не могут объяснить старые цены.
- Явно: «возврат браузера на сайт не является основанием для активации» (§5), «скриншот не подтверждение» (§6.4).
- Идемпотентность, дубликаты и out-of-order webhook (§7), `webhook_events`, `idempotency_keys` (§11).
- `cancel_at_period_end` отдельным полем (§8) — правильно, иначе теряется история отмен.

### 4.2. Проблемы

| # | Проблема | Почему важно |
|---|---|---|
| B-1 | **Объём.** ~30 сущностей + CRM (лиды, сделки, менеджеры, назначения), КП, возвраты, AI-кредиты, уведомления | Это продукт на 6–12 месяцев. Для стартапа без платящих клиентов — стоп-фактор |
| B-2 | **Не сказано, где живёт биллинг.** «Модульный монолит» — но внутри чего? | Если внутри SMM Studio — второй продукт его не переиспользует, цель §1 нарушена. Значит — отдельный сервис |
| B-3 | **Нет поведения при недоступности Core.** Что делает продукт, если entitlements не получены? | Без решения: либо падение Core = падение публикаций, либо бесплатный доступ при сбое (обход тарифа) |
| B-4 | **ЮKassa ≠ счёт для юрлица.** §6.3 требует счёт, но это не API провайдера, а ручной/ЭДО-процесс | Нужен «ручной» путь с первого дня, а не «потом»: первые клиенты — почти всегда юрлица |
| B-5 | **Нет модели тарифов продукта.** Какие тарифы, какие лимиты (проекты? каналы? посты? кредиты?), что единица учёта | Без этого `entitlements` и `plan_entitlements` не реализуемы — нечего ограничивать |
| B-6 | **Монетизация не выбрана:** подписка с лимитом постов или AI-кредиты | От этого зависит схема: `usage_events`/`credit_accounts` нужны или нет. Сейчас генерация вообще демо |
| B-7 | **Рекуррент платежей в РФ нестабилен** (3-DS на списании, отзывы согласий) | Нужен dunning и grace period с самого начала, а не как «расширение» |
| B-8 | **54-ФЗ и чеки при авансах/зачётах** упомянуты, но не превращены в требование к данным | Нужны поля чека и статуса фискализации в `payments`/`invoices` с самого начала, иначе переделка |
| B-9 | **Нет бэкапов и сверки.** §13 требует и то и другое, но текущий сервер не имеет описанного бэкапа | Платежи без бэкапа БД = потеря финансовой истории. Это блокер до запуска, а не «потом» |
| B-10 | **Порт 5432 открыт наружу** (известная проблема из handoff) | БД с деньгами и ПДн не может быть доступна из интернета |

## 6. Целевая архитектура

```
                    ┌──────────────────┐
   браузер ────────►│  id.yangrai.ru   │  Keycloak (OIDC)
                    │  только вход     │  пароли, verify, reset,
                    └────────┬─────────┘  сессии, MFA
                             │ OIDC code + PKCE
                             ▼
                    ┌──────────────────┐
   браузер ────────►│  core.yangrai.ru │  YANGRAI Core
                    │  профили, orgs,  │  members, roles, invites,
                    │  entitlements    │  catalog, orders, payments,
                    └────────┬─────────┘  subscriptions, invoices
                             │ HTTP API (внутренняя сеть)
                             ▼
                    ┌──────────────────┐
   браузер ────────►│  app.yangrai.ru  │  SMM Studio (BFF)
                    │  cookie-сессия   │  токены OIDC только на сервере
                    └──────────────────┘
```

**Ключевые решения:**

1. **IdP — только аутентификация.** Организации, роли, подписки — в Core. Это буквально §2 ТЗ.
2. **BFF.** Express обменивает code на токены, держит `HttpOnly` cookie. Фронт токенов не видит вовсе. Снимает §7 целиком.
3. **SSO между доменами — через редиректы IdP**, а не через общую cookie. Работает на любых доменах, не требует `encake.site` → `yangrai.ru` переезда ради SSO.
4. **Entitlements — отдельный API Core** с кэшем 30–60 с в продукте. Политика при сбое: **fail-closed для платных действий, grace 24 ч** для уже оплаченных (иначе падение Core останавливает публикации).
5. **Домены.** Если бренд — `yangrai.ru`, то `id.yangrai.ru` / `app.yangrai.ru`. `encake.site` тогда — временное имя до переезда, но redirect URI придётся поддерживать оба.

## 8. План интеграции

### 8.0. Два сценария

| | **A. «Первый рубль»** | **B. «Платформа по ТЗ»** |
|---|---|---|
| Цель | 5–10 платящих клиентов без автоматизации | Полный объём обоих ТЗ |
| Срок | 3–4 недели | 6–10 недель |
| Токены | **~120–170k** | **~400–600k** |
| Состав | вход, организации, изоляция данных, ручные счёта, простой paywall | + ЮKassa, trial, автопродление, CRM, кредиты, админка |
| Риск | мало автоматизации, ручная работа | долго без выручки, риск переделок |

**Рекомендация:** начать с A, но **модель данных делать сразу финальную** (7.1–7.3), чтобы переход к B был дописыванием, а не переделкой.

---

### Фаза 0. Закрыть доступ немедленно (0,5 дня, ~5k)

- Basic auth в nginx на `encake.site` (или временный общий пароль в приложении).
- Закрыть 5432 файрволом.
- Настроить `pg_dump` по cron + проверить восстановление.

**Готово, когда:** анонимный `GET /api/state` возвращает 401.

---

### Фаза 1. Решения и каркас (1 день, ~10k)

- Зафиксировать домены (`id.*`, `app.*`), IdP, SMTP-провайдера.
- Завести репозиторий Core (или monorepo), схему, миграции.
- Утвердить ER и API-контракты (это документ, не код).

**Готово, когда:** есть утверждённая схема БД и список эндпоинтов Core.

---

### Фаза 2. Identity MVP на Keycloak (1–1,5 недели, ~50–70k)

- Развернуть Keycloak на отдельном VPS, Postgres-база, HTTPS.
- Realm `yangrai`, клиент `smm-studio` (confidential, code+PKCE).
- Email-verify, сброс пароля, политики пароля, brute-force, сессии.
- Тема входа под бренд (минимум).

**Готово, когда:** можно зарегистрироваться, подтвердить email, войти, выйти, сбросить пароль; сессия отзывается.

---

### Фаза 3. Core: профиль, организации, роли (1,5–2 недели, ~60–90k)

- API: `GET /me`, `GET /orgs`, `POST /orgs`, `GET/PATCH /orgs/:id`,
  `GET /orgs/:id/members`, `POST /orgs/:id/invitations`, `POST /invitations/:token/accept`.
- Роли и проверка прав на backend.
- `audit_logs` для членства и ролей.
- Приглашения по email; принятие только для подтверждённого email.

**Готово, когда:** пользователь A не видит организацию B; приглашение нельзя принять чужим email; роль `member` не может менять участников.

---

### Фаза 4. Мультитенантность SMM Studio (2 недели, ~80–120k)

- Миграция: `org_id`, составной unique, перенос данных в первую организацию.
- OIDC-клиент + BFF-сессия + `requireUser` / `requireOrg`.
- Изоляция всех 18 роутов; правка `scheduler.js`, `publish.js`, `connect.js`.
- Убрать `cors()`; cookie `HttpOnly` + `Secure` + `SameSite=Lax`.
- Переключатель активной организации в UI.
- Тесты изоляции.

**Готово, когда:** два пользователя из разных организаций не видят проекты, каналы и посты друг друга — это проверяется автотестом, а не глазами.

---

### Фаза 5. Billing MVP (2–3 недели, ~90–130k)

- Каталог: `products`, `plans`, `plan_versions`, `limits`/`features`.
- `POST /orders`, `GET /orders/:id`, `POST /payments` (ссылка), `GET /payments/:id`.
- ЮKassa: `CreatePayment`, `GetPayment`, `VerifyWebhook`, idempotency, `webhook_events`, сверка.
- `subscriptions`: trial, active, past_due, suspended, expired, `cancel_at_period_end`.
- `invoices` + ручная сверка перевода (`PendingVerification`).
- Entitlements API + кэш в продукте + fail-closed.

**Готово, когда:** оплата активирует доступ только после webhook; повторный webhook не продлевает второй раз; счёт оплачен вручную — доступ включён; отмена автопродления сохраняет доступ до конца периода.

### Фаза 6. Paywall в продукте (1 неделя, ~30–50k)

- Лимиты: проекты, каналы, публикации в месяц.
- Экран тарифа и оплаты, статус подписки в интерфейсе.
- Публикация проверяет entitlement и на сервере (в том числе в планировщике).

**Готово, когда:** на исчерпанном лимите API возвращает 402, а не публикует.
