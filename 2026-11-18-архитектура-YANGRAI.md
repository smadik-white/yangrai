**Дата:** 18.11.2026  
**Статус:** рабочая версия для обсуждения

## 1. Контекст и допущения

- YANGRAI — SaaS-платформа для российского рынка. Первый продукт — SMM Studio (Node.js/Express + React).
- YANGRAI Core — новый сервис на ASP.NET Core: профили, организации, роли, каталог, подписки, платежи, entitlements.
- SMM Studio **интегрируется** с Core через OIDC и Entitlements API, а не переписывается на .NET. План — в [миграции](2026-11-18-миграция-smm-studio.md).
- Продавец — ИП на УСН, без НДС. Хостинг и персональные данные — в РФ.
- Домены: сейчас `encake.site`, до первых платежей — переезд на `yangrai.ru`.
- Платёжный провайдер — ЮKassa (первый), с абстракцией под второго.
- IdP — Keycloak на отдельном VPS.

## 2. Критика требований

| № | Требование | Что не так | Решение |
|---|---|---|---|
| 1 | Единый аккаунт | Легко смешать аккаунт, профиль и членство; соблазн объединять по email | `users` — глобальная сущность; членство и роли — per organization; email не первичный ключ; merge только после подтверждения владения |
| 2 | Единая подписка | Буквально «одна подписка на всё» ломает разные периоды, отмену одного продукта, разные юрлица и разную себестоимость | Единый **billing-контур**: один аккаунт, каталог, checkout, история. Подписки — per product; «всё в одном» — bundle-продукт |
| 3 | Автопродление | В РФ рекуррент нестабилен: 3-DS, истёкшие карты, МИР, жалобы на списания | Dunning, grace period, предуведомления, альтернативы (СБП, счёт), отмена в 2 клика, сохранение согласия |
| 4 | Пробный период | Без карты — абьюз; с картой — падение конверсии и жалобы; автоконверсия — риск чарджбэков | Trial на организацию, 7 дней, без автоконверсии, с лимитами и fingerprint |
| 5 | Ручная оплата менеджером | Менеджер, который сам включает доступ, — внутреннее мошенничество и расхождения в сверке | «Ручной» — провайдер платежа + 4 глаза + лимиты + аудит. Доступ — отдельным грантом, а не подделкой платежа |
| 6 | Роли и доступы | Смешение платформенных и продуктовых ролей; проверка прав только в UI | RBAC + resource-based policies; platform / org / product раздельно; RLS как второй слой |
| 7 | Масштабируемость | Преждевременные микросервисы; платежи — не узкое место | Модульный монолит, stateless API, очередь, партиционирование; выделение сервисов по триггерам |

### 2.1. Одна подписка на всё — плохая идея

У продуктов разные периоды, даты продления, себестоимость, договоры и юрлица. Один объект подписки означает:

- нельзя отменить один продукт, не затронув остальные;
- одна дата списания, неудобная клиенту;
- сложный proration при изменении состава;
- проблемы у холдингов с разными ИНН.

Правильно: **billing account = организация**, внутри — несколько подписок (по продукту), единый каталог, способ оплаты и история. «YANGRAI Pro за одну цену» — это bundle-продукт, а не особая сущность биллинга.

### 2.2. Trial с автоконверсией — источник жалоб

В РФ автосписание после trial без явного согласия почти гарантирует обращения в поддержку и чарджбэки. Trial **не конвертируется автоматически**: за 3 дня письмо, после окончания — free/ограниченный режим. Карта при регистрации — только для дорогих тарифов и с отдельным экраном согласия.

### 2.3. «Менеджер включает доступ» — внутреннее мошенничество

Менеджер заинтересован в активации, а не в факте денег. Если он может «подтвердить оплату», будут доступ без денег, расхождения в бухгалтерии и конфликт с бонусами. Решение: менеджер создаёт счёт и заявку, финансы подтверждают, в БД — constraint `approved_by <> claimed_by`. Бесплатный доступ — через `entitlement_grants`.

### 2.4. Микросервисы на старте — преждевременно

Команда 3–5 человек, низкий платёжный трафик. Микросервисы дадут распределённые транзакции, saga, дублирование и операционный груз. Нужен **модульный монолит** с границами модулей и возможностью выделить Billing/Entitlements позже.

## 3. Целевая архитектура

### 3.1. Принципы

1. **IdP — только аутентификация.** Пароли, сессии, MFA, сброс — Keycloak. Организации, роли, подписки — Core.
2. **Деньги и доступ разделены.** `payments` фиксируют деньги; `entitlements`/`grants` — права. Нельзя «оплатить» доступом и «выдать» платежом.
3. **Tenant (`org_id`) сквозной.** EF Core global filter + PostgreSQL RLS.
4. **Всё, что меняет деньги/доступ, идемпотентно и журналируется.** Outbox, `idempotency_keys`, `audit_logs`.
5. **Продукты не знают о платежах.** Только entitlements и usage.
6. **Карточные данные не храним.** Только токены провайдера.
7. **Один стек — не самоцель.** Keycloak на Java — допустимое инфраструктурное исключение.

### 3.5. IdP: Keycloak или .NET?

| Вариант | Стек | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| **Keycloak** | Java | MFA, verify, reset, brute-force, админка, темы | JVM ~1–1,5 ГБ, отдельный VPS | **Рекомендован** |
| OpenIddict | .NET | Один стек, Apache 2.0 | Регистрацию, verify, reset, MFA, защиту от перебора пишете сами | Резерв |
| Duende IdentityServer | .NET | Зрелый, поддержка | Коммерческая лицензия | Если есть бюджет |
| Zitadel | Go | Лёгкий, организации | Дублирует организации Core | Альтернатива |
| Auth0 / Clerk | SaaS | Быстро | ПДн за границей, 152-ФЗ | Не подходит |

Keycloak — инфраструктурный компонент, а не код платформы. При .NET-команде эксплуатация контейнера проще, чем 2–3 недели собственной security-логики.

### 3.6. Контракт интеграции продуктов

1. OIDC-клиент (confidential, code+PKCE) + собственная BFF-сессия продукта.
2. `org_id` в БД продукта; все запросы фильтруются.
3. Entitlements:

```http
GET /internal/v1/orgs/{orgId}/entitlements
Authorization: Bearer <service-token>
X-Request-Id: ...
```

```json
{
  "org_id": "…",
  "etag": "v42",
  "valid_until": "2026-12-01T00:00:00Z",
  "features": {
    "smm.projects.max": { "enabled": true, "limit": 3 },
    "smm.posts.month": { "enabled": true, "limit": 150, "used": 42 },
    "smm.ai_images.month": { "enabled": true, "limit": 100, "used": 7 }
  }
}
```

4. Кэш 30–60 секунд по ETag.
5. При недоступности Core: **fail-closed для новых платных действий**, **grace 24 часа** для уже оплаченных.
6. Usage-события — асинхронно и идемпотентно:

```http
POST /internal/v1/orgs/{orgId}/usage-events
{ "feature": "smm.posts", "quantity": 1, "idempotency_key": "post:…", "occurred_at": "…" }
```

### 3.7. Окружения и деплой

- **dev** — локально, Docker Compose, sandbox-платежи.
- **staging** — отдельная БД, отдельный realm Keycloak, sandbox.
- **prod** — РФ-облако: Yandex Cloud / VK Cloud / Selectel; managed PostgreSQL, Redis, Object Storage, ALB, KMS/Lockbox.

Для MVP не нужен Kubernetes: 2 app-VM за балансировщиком + managed DB + Redis + отдельная VM под Keycloak. K8s — при 5+ сервисах или потребности в автоскейлинге.

CI/CD: GitLab CI (РФ-дружественный) или GitHub Actions. Build → unit/integration → SAST/Trivy → миграции (отдельный job с бэкапом) → deploy (blue-green) → smoke.

### 4.2. DDL

Деньги — целые в копейках (`bigint`), даты — `timestamptz` UTC, ID — UUIDv7 (генерируются приложением), email — `citext`, но **не первичный ключ**.

### 4.3. Тенантность и RLS

Два слоя:

1. **EF Core global query filter** — `HasQueryFilter(e => e.OrgId == _tenant.OrgId)`. В фоновых задачах тенант выставляется явно.
2. **PostgreSQL RLS**:

```sql
alter table subscriptions enable row level security;
alter table subscriptions force row level security;

create policy tenant_isolation on subscriptions
  using (org_id = nullif(current_setting('app.org_id', true), '')::uuid);
```

На каждый запрос/транзакцию:

```sql
select set_config('app.org_id', $1, true);
```

Нюансы:

- `force row level security` обязателен, иначе владелец таблицы обходит политику.
- Приложение ходит под ролью без `bypassrls`.
- PgBouncer в transaction pooling: `SET LOCAL` сбрасывается при коммите.
- Админские запросы — отдельная роль с `bypassrls`, только `/admin`, с аудитом.

### 4.4. Замечания по деньгам и датам

- Только `bigint` в копейках + `currency` + `vat_rate_bp`. Никаких `float`.
- `vat_rate_bp = 0` для ИП на УСН; ставка — конфигурация, не константа.
- Снимок названия, цены, НДС и периода — в `order_items`/`invoices`; старые заказы не пересчитываются.
- Даты периода — UTC, `anchor_day` 1–31 с клампингом на короткие месяцы; тесты обязательны.
- UUIDv7 для time-ordered индексов; `bigserial` для логов и событий.
- Мягкое удаление: `status='deleted'`, email анонимизируется, финансовые документы сохраняются.

## 5. Биллинг

### 5.1. Жизненный цикл

```
trialing ──(trial_end, оплата)──► active
trialing ──(trial_end, нет оплаты)──► expired / free
active ──(renewal failed)──► past_due ──(grace)──► suspended ──(90 дней)──► expired
past_due ──(оплата)──► active
suspended ──(оплата)──► active
active ──(cancel_at_period_end)──► canceled (доступ до конца периода)
```

- `canceled` — пользователь отменил, доступ до `period_end`.
- `expired` — доступа нет.
- `suspended` — read-only, публикации остановлены, данные сохранены.

### 5.2. Trial

- 7 дней, на организацию, без карты, без автоконверсии.
- Функции — как у «Про»; после окончания — read-only 30 дней, данные 90 дней.
- Один trial на организацию/ИНН; fingerprint.
- Продление — только через `entitlement_grants`.

### 5.3. Продление и dunning

Ежедневный job (05:00 МСК):

1. Подписки с `period_end <= now() + 3 days`, `cancel_at_period_end = false`.
2. `order` с idempotency-ключом `renew:{subscription_id}:{period_end:yyyyMMdd}`.
3. Списание сохранённым методом; если метода нет — счёт и письмо.
4. Успех: `period_start = old period_end`, `period_end = add_period(...)`, `active`, событие, outbox.
5. Неудача: `past_due`, расписание повторов.

| День | Действие |
|---|---|
| D0 | Неудача, письмо, повтор через 24 ч |
| D+1, D+3, D+7 | Повторы |
| D+5 | `past_due`: доступ есть, баннер |
| D+10 | `suspended`: read-only, публикации остановлены |
| D+40 | `expired`, downgrade, retention 90 дней |

Перед списанием — письмо за 3 дня (месяц) / 7 дней (год). Отмена — в 2 клика.

### 5.4. Ручная оплата

1. Клиент запрашивает счёт; менеджер создаёт `order` + `invoice`, PDF.
2. Клиент платит банковским переводом.
3. Менеджер фиксирует `manual_payment_claim` (дата, сумма, платёжка, документ).
4. Финансы подтверждают; `approved_by <> claimed_by`.
5. Платёж `succeeded`, подписка активируется.
6. Бухгалтерия: акт/УПД, ЭДО — позже.

Правила: менеджер не меняет статус подписки напрямую; 4 глаза всегда; `manual` — провайдер платежа, а не «режим без денег»; ежедневная сверка; SLA активации — 1 рабочий день.

### 5.5. Изменение тарифа и proration

- Апгрейд: доплата за оставшиеся дни; формула и округление фиксируются.
- Даунгрейд: со следующего периода, без возврата.
- Смена периода: в MVP — с начала следующего периода.
- Места: добавление — пропорционально; уменьшение — со следующего периода.
- В MVP — `preview-change` + явное подтверждение, без «тихих» списаний.

### 5.6. Цены и версии

- `plan_versions` и `plan_prices` иммутабельны; изменение цены — новая версия.
- Подписка хранит `plan_version_id`.
- При продлении: grandfathering или переход на новую версию после уведомления за 30 дней.
- Годовая цена фиксируется на год.

### 5.7. Возвраты

- В MVP — вручную: `refunds` + API провайдера + чек возврата.
- Доступ после возврата — по политике (сразу или до конца периода), зафиксированной в оферте.
- Чарджбэк: шаблон доказательств (логи, IP, акцепт оферты, письма).

### 5.8. 54-ФЗ, НДС, чеки

- Фискализация — на стороне провайдера; в `payments` — `fiscal_receipt_id`, `receipt_url`, `fiscal_status`.
- Чек: услуга, сумма, НДС, email/телефон; для ИП на УСН — «без НДС».
- Применимость ККТ к безналу B2B — решение бухгалтера; поля в модели есть.
- Налоговый режим продавца — конфигурация (`tax_mode`, `vat_rate_bp`), не хардкод.

### 5.9. Провайдеры и вебхуки

```csharp
public interface IPaymentProvider
{
    string Code { get; }
    Task<CreatedPayment> CreateAsync(CreatePaymentRequest request, CancellationToken ct);
    Task<PaymentState> GetAsync(string providerPaymentId, CancellationToken ct);
    Task<RefundResult> RefundAsync(string providerPaymentId, long amountMinor, CancellationToken ct);
    Task<RecurringResult> ChargeSavedAsync(string methodToken, CreatePaymentRequest request, CancellationToken ct);
    bool VerifyWebhook(HttpRequest request, string body, out string eventId);
}
```

Обработка вебхука:

1. Подпись + IP allowlist + timestamp (±5 минут).
2. Вставка в `webhook_events` (`unique(provider, event_id)`); дубликат — 200.
3. Быстрый 200.
4. Worker: `FOR UPDATE SKIP LOCKED`, **перезапрос платежа у провайдера**, проверка суммы/валюты/заказа, транзакция, outbox.
5. Ошибка → retry, затем DLQ + алерт.

Вебхук — подсказка; источник истины — `GetPayment` + ежедневная сверка.

### 5.10. Сверка

- Ежедневно: платежи провайдера ↔ `payments`; пропуски/лишние/суммы.
- Еженедельно: банковская выписка ↔ ручные заявки.
- Ежемесячно: выручка, возвраты, НДС, отчёт в 1С.
- Алерт при расхождении > 0.

```csharp
builder.Services.AddAuthorization(o =>
{
    o.AddPolicy("billing:manage", p => p
        .RequireAuthenticatedUser()
        .AddRequirements(new OrgPermissionRequirement("billing.manage")));
});

public sealed class OrgPermissionHandler(IPermissionService permissions)
    : AuthorizationHandler<OrgPermissionRequirement>
{
    protected override async Task HandleRequirementAsync(
        AuthorizationHandlerContext context, OrgPermissionRequirement req)
    {
        if (context.Resource is not HttpContext http) return;
        var orgId = http.GetRouteValue("orgId")?.ToString();
        if (orgId is null) return;

        if (await permissions.HasAsync(http.User.GetSubjectId(), orgId, req.Permission))
            context.Succeed(req);
    }
}
```

## 9. Масштабируемость и эксплуатация

| Слой | Решение |
|---|---|
| API | Stateless, горизонтально; сессии в Redis/БД |
| PostgreSQL | Primary + read replica; PgBouncer; партиционирование `audit_logs`, `webhook_events`, `usage_counters` после ~10 млн строк |
| Redis | Сессии, кэш entitlements (30–60 с), rate limit, блокировки |
| Worker | Hangfire на Postgres; очереди `billing`, `webhooks`, `emails`; идемпотентные задания; advisory locks |
| События | Outbox → диспетчер; at-least-once; потребители идемпотентны; RabbitMQ — позже |
| Файлы | S3 + signed URL; lifecycle |
| Почта | Провайдер API; SPF/DKIM/DMARC; bounce handling |

Ёмкость MVP: 10 тыс. организаций, 50 тыс. пользователей, 1 млн платежей в год — единицы rps. Узкое место — письма, PDF и внешние API, не БД.

Триггеры выделения сервисов: p95 > 300 мс → реплика/кэш; CPU БД > 70% → партиции/апгрейд; lag worker > 5 мин → воркеры; > 3 продуктовых команд → Billing/Entitlements в отдельный сервис.

Надёжность: SLO 99,9%, p95 < 300 мс; RPO 5 мин, RTO 1 ч; full backup + WAL PITR; учебное восстановление раз в квартал; blue-green; expand-contract миграции.

Наблюдаемость: OpenTelemetry, `request_id`/`org_id`/`payment_id`; метрики успешности платежей, лага вебхуков, trial conversion, dunning recovery, p95 entitlements; алерты.

Безопасность: OWASP ASVS L2, пентест; секреты в Lockbox/Vault; TLS 1.3; БД at rest; токены провайдера AES-256-GCM; 152-ФЗ (уведомление РКН, локализация, согласия, DSR, инцидент 24 ч); 54-ФЗ на стороне провайдера.

## 11. План

**Команда:** 2 backend (.NET), 1 frontend (React/TS), 1 QA/DevOps, PM/дизайн part-time, бухгалтер/юрист part-time.

| Фаза | Срок | Содержание | Критерий готовности |
|---|---|---|---|
| 0. Решения | 1 нед. | Юрлицо, домены, провайдер, SMTP, РКН, оферта | Подписанные решения |
| 1. Каркас | 2 нед. | Монорепо, CI/CD, инфраструктура, Keycloak, BFF, БД, staging, OTel | Вход через OIDC, `/me`, деплой |
| 2. Тенанты | 2–3 нед. | orgs, members, invitations, roles, audit, org switcher, RLS | Тесты изоляции |
| 3. Каталог + ручной биллинг | 3 нед. | plans/prices, orders, invoices, manual claims, entitlements, grants, paywall | Счёт оплачен вручную → доступ |
| 4. Онлайн-платежи | 3–4 нед. | Провайдер, вебхуки, идемпотентность, методы, рекуррент, trial, dunning, чеки, возвраты | Карта → доступ; продление; dunning; отмена |
| 5. Hardening | 2 нед. | Нагрузка, безопасность, DR, runbook, поддержка | SLO, чек-лист запуска, пентест |

Итого ~13–16 недель до автопродления; «первый рубль» вручную — 6–8 недель. Один backend — 5–6 месяцев.

**MVP-cut:** без микросервисов, Kubernetes, GraphQL, event sourcing, своего IdP, хранения карт, автоматического proration, AI-кредитов, мультивалютности, self-service возвратов, SAML, партнёрского портала.
